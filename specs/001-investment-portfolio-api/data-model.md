# Data Model: API de Inversiones — Portfolio, Instrumentos, Órdenes e Idempotencia

**Feature**: 001-investment-portfolio-api | **Date**: 2026-11-12 | **Plan**: [plan.md](./plan.md)

Esquema autoritativo: sección 3 de la [spec](./spec.md). Persistencia: PostgreSQL 14+ con migraciones Liquibase
(`ddl-auto: none`). Convenciones: UTC, `LocalDateTime`, `TIMESTAMP WITHOUT TIME ZONE`, `NUMERIC(10,2)` para
importes/precios/cantidades, `BIGINT GENERATED BY DEFAULT AS IDENTITY` para PK.

## 1. `users`

Representa las cuentas habilitadas para operar. La identificación es por `account_number` (cabecera
`X-AccountNumber`).

| Columna | Tipo | Restricciones | Java |
|---|---|---|---|
| `id` | `BIGINT` | PK, `GENERATED BY DEFAULT AS IDENTITY` | `Long` |
| `email` | `VARCHAR(150)` | NOT NULL, UNIQUE | `String` |
| `account_number` | `VARCHAR(50)` | NOT NULL, UNIQUE | `String` |

**Índices**: `UNIQUE (account_number)` — obligatorio, no solo de rendimiento: el `SELECT … FOR NO KEY UPDATE`
sobre un predicado sin índice bloquea **todas las filas que el scan toca**, serializando cuentas no
relacionadas y generando deadlocks (research R-004).

**Invariantes**
- `email` y `account_number` son únicos y no nulos.
- No hay autenticación: la fila es puramente referencial.

**Rol en el dominio**: la fila `users` es el **mutex** de la cuenta. `PESSIMISTIC_WRITE` sobre ella serializa
todas las operaciones que compiten por los recursos de esa cuenta.

## 2. `instruments`

Catálogo de instrumentos.

| Columna | Tipo | Restricciones | Java |
|---|---|---|---|
| `id` | `BIGINT` | PK, identity | `Long` |
| `ticker` | `VARCHAR(20)` | NOT NULL, UNIQUE | `String` |
| `name` | `VARCHAR(150)` | NOT NULL | `String` |
| `type` | `VARCHAR(20)` | NOT NULL, CHECK ∈ {`ACCIONES`,`MONEDA`} | `InstrumentType` (enum) |

**Invariantes**
- Solo dos tipos: `ACCIONES` y `MONEDA` (spec D-048). Restricción `CHECK` en la base.
- Existe exactamente un instrumento de tipo `MONEDA`: `ARS` / `Peso argentino` / `MONEDA` (spec §3.2).
- `ARS` **aparece en el catálogo** de instrumentos (decisión Q-02) pero **no es operable** como `BUY`/`SELL`.
- `BUY`/`SELL` solo sobre `ACCIONES`; `CASH_IN`/`CASH_OUT` solo sobre `ARS` (spec FR-021, FR-022).

**Búsqueda** (FR-009): coincidencia parcial e insensible a mayúsculas sobre `ticker` y `name`, sin duplicados.
Implementación: `WHERE lower(ticker) LIKE lower(concat('%', :query, '%')) OR lower(name) LIKE ...`. La condición
es una disyunción sobre la **misma fila**, por lo que no puede duplicar resultados.

## 3. `orders`

Tabla central. **Todas** las operaciones del usuario se registran aquí: compras, ventas y transferencias.

| Columna | Tipo | Restricciones | Java |
|---|---|---|---|
| `id` | `BIGINT` | PK, identity | `Long` |
| `user_id` | `BIGINT` | FK → `users.id`, NOT NULL | `Long` |
| `instrument_id` | `BIGINT` | FK → `instruments.id`, NOT NULL | `Long` |
| `side` | `VARCHAR(20)` | NOT NULL, CHECK ∈ {`BUY`,`SELL`,`CASH_IN`,`CASH_OUT`} | `OrderSide` |
| `size` | `NUMERIC(10,2)` | NOT NULL, CHECK (`size` > 0) | `BigDecimal` |
| `price` | `NUMERIC(10,2)` | NULL, CHECK (`price` IS NULL OR `price` > 0) | `BigDecimal` |
| `type` | `VARCHAR(20)` | NOT NULL, CHECK ∈ {`MARKET`,`LIMIT`} | `OrderType` |
| `status` | `VARCHAR(20)` | NOT NULL, CHECK ∈ {`NEW`,`FILLED`,`REJECTED`,`CANCELLED`} | `OrderStatus` |
| `rejection_reason` | `VARCHAR(500)` | NULL | `String` |
| `datetime` | `TIMESTAMP` | NOT NULL | `LocalDateTime` |

**Semántica dual de `size`** (spec D-045, research R-016): una única columna con dos significados según `side`.
- `BUY` / `SELL` → **cantidad de acciones** (siempre entera).
- `CASH_IN` / `CASH_OUT` → **importe en pesos**.

En el dominio se tipa con value objects distintos (`ShareQuantity`, `CashAmount`) para impedir la mezcla de
semánticas; el esquema conserva la columna única.

**Invariantes**
1. `size > 0` siempre.
2. `price IS NULL OR price > 0`.
3. `side ∈ {BUY, SELL}` ⟹ `instrument.type = 'ACCIONES'`.
4. `side ∈ {CASH_IN, CASH_OUT}` ⟹ `instrument.ticker = 'ARS'` y `type = 'MARKET'`.
5. `side ∈ {CASH_IN, CASH_OUT}` ⟹ `status = 'FILLED'` (nunca `NEW` ni `CANCELLED`) y `price IS NULL`.
6. `type = 'LIMIT'` ⟹ `price IS NOT NULL`.
7. `type = 'MARKET'` ⟹ el request **no** trae precio (se valida en el borde; la fila usa el precio de
   ejecución resuelto).
8. `side ∈ {BUY, SELL}` ⟹ `size` es entera.
9. `status = 'REJECTED'` ⟹ `rejection_reason IS NOT NULL`.
10. `datetime` en UTC, asignado por el servidor.

**Las invariantes 3–5, 8 y 9 son reglas de negocio**, no de entrada: se validan en el caso de uso y una
violación produce una orden `REJECTED` (no un error HTTP) cuando es posible. Las que dependen del request
(tipos, precio presente/ausente, `size` vs `amount`) se validan en el borde → `400`.

**Transiciones de estado**

```text
                 ┌──────────────────────────────┐
   crear ───────▶│  validate → decidir estado   │
                 └──────────────┬───────────────┘
                                │
        ┌───────────────────────┼────────────────────────┐
        │                       │                        │
   MARKET ok              LIMIT ok              regla negocio
   o transferencia                                violada
        │                       │                        │
        ▼                       ▼                        ▼
     ┌─────────┐            ┌────────┐             ┌──────────┐
     │ FILLED  │            │  NEW   │             │ REJECTED │
     └─────────┘            └───┬────┘             └──────────┘
        │                       │
        │  cancelar (NEW)       │
        └───────────────────────┼──────▶ ┌───────────┐
                                │        │ CANCELLED │
                                └────────┴───────────┘

   FILLED, REJECTED, CANCELLED  →  terminales, inmutables (BR-004)
   CASH_IN / CASH_OUT  →  siempre FILLED, nunca cancelables (BR-007)
```

**Índices**

| Índice | Columnas | Propósito |
|---|---|---|
| `idx_orders_user_datetime` | `(user_id, datetime DESC)` | Historial de la cuenta, orden descendente (FR-080) |
| `idx_orders_user_status_datetime` | `(user_id, status, datetime DESC)` | Historial filtrado por estado (FR-084) |
| `idx_orders_instrument_status` | `(instrument_id, status)` | Posiciones por instrumento (FR-069) |
| `idx_orders_user_instrument_status_dt_id` | `(user_id, instrument_id, status, datetime, id)` | Soporte del fold de costo promedio: filtra y provee el **orden total** (research R-009, R-010) |

El último índice es crítico para el cálculo del costo promedio: el desempate por `id` (monótona) garantiza que
dos lecturas concurrentes calculen el mismo costo promedio para la misma posición.

## 4. `marketdata`

Cotizaciones. Precargadas; su carga/actualización está fuera de alcance (D-031).

| Columna | Tipo | Restricciones | Java |
|---|---|---|---|
| `id` | `BIGINT` | PK, identity | `Long` |
| `instrument_id` | `BIGINT` | FK → `instruments.id`, NOT NULL | `Long` |
| `high` | `NUMERIC(10,2)` | NOT NULL, CHECK (> 0) | `BigDecimal` |
| `low` | `NUMERIC(10,2)` | NOT NULL, CHECK (> 0) | `BigDecimal` |
| `open` | `NUMERIC(10,2)` | NOT NULL, CHECK (> 0) | `BigDecimal` |
| `close` | `NUMERIC(10,2)` | NOT NULL, CHECK (> 0) | `BigDecimal` |
| `previous_close` | `NUMERIC(10,2)` | NOT NULL, CHECK (> 0) | `BigDecimal` |
| `datetime` | `TIMESTAMP` | NOT NULL | `LocalDateTime` |

**Restricciones**
- Todos los valores de cotización son positivos.
- `high >= low`.
- `UNIQUE (instrument_id, datetime)` — evita cotizaciones duplicadas del mismo instante.

**Invariantes de dominio (no de base)**
- La **última cotización** de un instrumento es la fila con mayor `datetime`.
- Un `close` nulo, cero o negativo se considera **no disponible**: no se usa para ejecutar órdenes `MARKET`
  ni para valuar posiciones.
- `previous_close` en cero o ausente ⟹ el rendimiento diario se informa como **no disponible** (FR-075), sin
  división por cero.

**Índice**: `(instrument_id, datetime DESC)` — subrange directo de "última cotización por instrumento".

## 5. `idempotency_keys`

Garantiza que una misma operación no se procese más de una vez ante reintentos (spec §7, D-043).

| Columna | Tipo | Restricciones | Java |
|---|---|---|---|
| `id` | `BIGINT` | PK, identity | `Long` |
| `user_id` | `BIGINT` | FK → `users.id`, NOT NULL | `Long` |
| `idempotency_key` | `VARCHAR(255)` | NOT NULL | `String` |
| `request_hash` | `VARCHAR(64)` | NOT NULL | `String` |
| `order_id` | `BIGINT` | FK → `orders.id`, NOT NULL, **UNIQUE** | `Long` |
| `created_at` | `TIMESTAMP` | NOT NULL | `LocalDateTime` |

**Restricciones**
- `UNIQUE (user_id, idempotency_key)` — la clave es única **por cuenta** (FR-055).
- `UNIQUE (order_id)` — cada orden está vinculada a **como máximo** un registro de idempotencia, y cada
  registro está asociado a **exactamente** una orden (FK NOT NULL).

**Invariantes**
- `request_hash` es SHA-256 en hexadecimal (64 chars) del contenido semántico canonicalizado
  (research R-017): `ticker | side | type | size|amount | price`, con normalización de mayúsculas,
  `stripTrailingZeros()` y `toPlainString()`.
- El hash es **independiente del orden de las propiedades JSON** (FR-056).
- `size` y `amount` son **mutuamente excluyentes** en el request (D-011), por lo que el hash cubre exactamente
  uno de los dos.
- Las claves **no se eliminan** mientras la orden asociada deba seguir siendo consultable de forma idempotente
  (FR-061).

**Índices**: `UNIQUE (user_id, idempotency_key)` y `UNIQUE (order_id)` ya son índices únicos en PostgreSQL; no
se duplican (spec §3.8).

## Agregaciones derivadas (no persistidas)

Nada de esto se materializa en tablas: se calcula desde `orders` en cada consulta (D-047).

### Efectivo

```sql
-- efectivo total
COALESCE(SUM(o.size * o.price) FILTER (WHERE o.side IN ('BUY','SELL')), 0)  -- signo según side
```

Fórmula completa (BR-008):

```
efectivoTotal = Σ(CASH_IN FILLED) − Σ(CASH_OUT FILLED)
               − Σ(BUY FILLED: size×price) + Σ(SELL FILLED: size×price)

efectivoReservado  = Σ(size×price) de BUY en estado NEW
efectivoDisponible = efectivoTotal − efectivoReservado
```

Notas:
- `SUM` sobre un conjunto vacío devuelve `NULL` en PostgreSQL → el `COALESCE` es obligatorio, y el `FILTER`
  va **dentro** del `COALESCE`.
- Las transferencias no llevan precio (`price IS NULL`), por lo que su importe es `size` y no `size×price`.
  El cálculo de efectivo distingue los tres casos por `side`, no por fórmula uniforme.

### Posiciones

```
cantidadTotal     = Σ(BUY FILLED.size) − Σ(SELL FILLED.size)          por instrumento
cantidadReservada = Σ(SELL NEW.size)                                    por instrumento
cantidadDisponible= cantidadTotal − cantidadReservada
```

### Costo promedio (fold ordenado — research R-009)

**No es un agregado.** Se calcula recorriendo las órdenes `FILLED` del par (cuenta, instrumento) ordenadas por
`(datetime ASC, id ASC)`:

```text
qty = 0 ; cost = 0
para cada orden o en orden ascendente:
    si o.side == BUY:
        qty  += o.size
        cost += o.size * o.price
    si o.side == SELL:
        avg = cost / qty          (qty > 0 garantizado)
        cost -= o.size * avg
        qty  -= o.size
costoPromedio = (qty == 0) ? 0 : cost / qty
```

Precisión: se conserva la precisión completa de `BigDecimal` internamente (divisiones con
`MathContext.DECIMAL128`); el redondeo a 2 decimales ocurre **solo en el borde de la API** (BR-015, D-050).

### Rendimientos

```
valorDePosicion = cantidadTotal × último close

rendimientoTotal  = ((valorDePosicion − costoAdquisicion) / costoAdquisicion) × 100
                    → null si costoAdquisicion es null o 0        (FR-075)

rendimientoDiario = ((close − previousClose) / previousClose) × 100
                    → null si previousClose es null o 0          (FR-075)
```

### Patrimonio

```
valorTotalPortfolio = efectivoTotal + Σ(valorDePosicion)   (BR-013)
```

Las órdenes `NEW` **no** entran en estas sumas: solo reducen la disponibilidad (BR-019, D-040).

## Estrategia transaccional y de concurrencia

| Aspecto | Decisión | Referencia |
|---|---|---|
| Unidad transaccional | Una operación de negocio = una transacción `REQUIRED` | research R-007 |
| Nivel de aislamiento | `READ COMMITTED` (default de PostgreSQL). **No** usar `REPEATABLE READ`/`SERIALIZABLE` | research R-004 |
| Mutex | Fila `users` con `@Lock(PESSIMISTIC_WRITE)` → `FOR NO KEY UPDATE` | research R-004 |
| Momento del lock | **Primera** sentencia de la transacción, antes de leer agregados | research R-004 |
| Límite de espera | `SET LOCAL lock_timeout` como primera sentencia | research R-006 |
| Orden de locks | `users` → `idempotency_keys` (solo lectura) → `orders` (sin lock) → INSERTs | research R-005 |
| Propagación | `REQUIRED` en toda la cadena. **Prohibido** `REQUIRES_NEW` (rompe atomicidad) y `NESTED` (sin savepoints con Hibernate) | research R-007 |
| Lecturas | `@Transactional(readOnly = true)`; los GET **no** toman el lock de la cuenta | research R-007 |
| Flush | `saveAndFlush` de la orden **antes** de insertar la clave de idempotencia (orden de FK) | research R-007 |
| Idempotencia | Lock de cuenta → lookup por `(user_id, key)` → insert | research R-007 |
| Hash mismatch | `409 Conflict`; hash coincidente → replay con `201` y la orden original | spec FR-057, FR-058 |

### Atomicidad de una creación de orden

```text
BEGIN (READ COMMITTED)
  SET LOCAL lock_timeout = '2s'                     -- 1. acotar espera
  SELECT * FROM users WHERE account_number = ?      -- 2. FOR NO KEY UPDATE  ← MUTEX
        FOR NO KEY UPDATE                            --    404 si no existe
  SELECT * FROM idempotency_keys                    -- 3. ¿replay?
    WHERE user_id = ? AND idempotency_key = ?
        → hash igual  → devolver orden original (201), sin escribir nada
        → hash distinto → 409
  SELECT agregados FROM orders ...                 -- 4. saldos y cantidades
  validar reglas de negocio                        -- 5. ¿rechazo? → orden REJECTED
  INSERT INTO orders ...                           -- 6. orden
  INSERT INTO idempotency_keys ...                 -- 7. clave  (FK → orders.id)
COMMIT                                             -- 8. libera el lock
```

Si cualquier paso falla, **todo** se revierte: ni la orden ni la clave quedan persistidas (FR-060).

### Cancelación

Mismo patrón: lock de la cuenta → leer la orden filtrando por cuenta → si el estado no es `NEW`, `409` → si no
existe o pertenece a otra cuenta, `404` → cambiar a `CANCELLED` (libera la reserva por exclusión del cálculo).
La liberación de reservas es **implícita**: las reservas se derivan de las órdenes `NEW`, y al pasar a
`CANCELLED` dejan de contarse.
