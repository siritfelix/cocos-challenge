# Especificación de Requerimientos – Challenge Backend Java

## 1. Propósito y alcance

Desarrollar una API REST para administrar un portfolio de inversiones, consultar instrumentos financieros, gestionar órdenes de compra y venta, y realizar transferencias de efectivo.

El sistema debe permitir:

- Consultar el portfolio de una cuenta.
- Consultar instrumentos disponibles.
- Crear órdenes de compra (`BUY`).
- Crear órdenes de venta (`SELL`).
- Realizar ingresos de efectivo (`CASH_IN`).
- Realizar retiros de efectivo (`CASH_OUT`).
- Consultar el historial de órdenes.
- Cancelar órdenes pendientes.
- Calcular saldos disponibles, posiciones y rendimientos.
- Garantizar atomicidad, concurrencia e idempotencia en las operaciones.

El sistema no debe simular operaciones de mercado ni disponer de un motor de matching.

Las cotizaciones de los instrumentos estarán precargadas en la base de datos.

## 2. Stack tecnológico

Se utilizarán las siguientes tecnologías:

- Java 21.
- Spring Boot 4.
- Spring Web.
- Spring Data JPA.
- Hibernate.
- PostgreSQL.
- Liquibase para migraciones de base de datos.
- Maven como herramienta de construcción.
- JUnit y Mockito para pruebas unitarias.
- Testcontainers para pruebas de integración.
- Pruebas funcionales de los endpoints REST.
- Docker y docker compose para levantar en local sin instalar nada.

Se utilizarán transacciones de base de datos y bloqueos pesimistas para garantizar la consistencia de las operaciones concurrentes.

Los importes, precios y cantidades se manejarán en Java mediante `BigDecimal`.

## 3. Modelo de datos

El modelo de datos estará compuesto por cinco tablas:

1. `users`
2. `instruments`
3. `orders`
4. `marketdata`
5. `idempotency_keys`

No se crearán tablas adicionales para posiciones ni saldos. Ambos se calcularán a partir de las órdenes registradas.

### 3.1. Tabla users

Representa las cuentas habilitadas para operar en el sistema.

| Campo | Tipo PostgreSQL | Restricciones |
|---|---|---|
| id | BIGINT GENERATED BY DEFAULT AS IDENTITY | PK |
| email | VARCHAR(150) | NOT NULL, UNIQUE |
| account_number | VARCHAR(50) | NOT NULL, UNIQUE |

La identificación de la cuenta se realizará mediante el campo `account_number`.

No se implementará autenticación ni administración de credenciales.

### 3.2. Tabla instruments

Representa el catálogo de instrumentos disponibles.

| Campo | Tipo PostgreSQL | Restricciones |
|---|---|---|
| id | BIGINT GENERATED BY DEFAULT AS IDENTITY | PK |
| ticker | VARCHAR(20) | NOT NULL, UNIQUE |
| name | VARCHAR(150) | NOT NULL |
| type | VARCHAR(20) | NOT NULL |

Los únicos tipos de instrumentos permitidos serán:

- `ACCIONES`
- `MONEDA`

El instrumento correspondiente al efectivo será:

- ticker: `ARS`
- name: `Peso argentino`
- type: `MONEDA`

Las operaciones de compra y venta solamente podrán realizarse sobre instrumentos de tipo `ACCIONES`.

Las operaciones de ingreso y retiro de efectivo solamente podrán realizarse sobre el instrumento `ARS`.

### 3.3. Tabla orders

Es la tabla central del sistema. Todas las operaciones realizadas por los usuarios deberán registrarse en ella.

Incluye compras, ventas y transferencias de efectivo.

| Campo | Tipo PostgreSQL | Restricciones |
|---|---|---|
| id | BIGINT GENERATED BY DEFAULT AS IDENTITY | PK |
| user_id | BIGINT | FK a users.id, NOT NULL |
| instrument_id | BIGINT | FK a instruments.id, NOT NULL |
| side | VARCHAR(20) | NOT NULL |
| size | NUMERIC(10,2) | NOT NULL |
| price | NUMERIC(10,2) | NULL |
| type | VARCHAR(20) | NOT NULL |
| status | VARCHAR(20) | NOT NULL |
| rejection_reason | VARCHAR(500) | NULL |
| datetime | TIMESTAMP WITHOUT TIME ZONE | NOT NULL |

Valores permitidos:

**side**

- `BUY`
- `SELL`
- `CASH_IN`
- `CASH_OUT`

**type**

- `MARKET`
- `LIMIT`

**status**

- `NEW`
- `FILLED`
- `REJECTED`
- `CANCELLED`

Reglas de integridad:

- `size` debe ser mayor que cero.
- `price` debe ser mayor que cero cuando tenga valor.
- Las órdenes BUY y SELL deben operar sobre instrumentos de tipo ACCIONES.
- Las operaciones CASH_IN y CASH_OUT deben utilizar el instrumento ARS.
- Las operaciones CASH_IN y CASH_OUT deben ser de tipo MARKET.
- Las operaciones CASH_IN y CASH_OUT deben ejecutarse inmediatamente y quedar en estado FILLED.
- Las operaciones CASH_IN y CASH_OUT no pueden quedar en estado NEW ni CANCELLED.
- Las órdenes BUY y SELL de tipo LIMIT requieren un precio.
- Las órdenes BUY y SELL de tipo MARKET no permiten enviar un precio en el request.
- Las cantidades de instrumentos para BUY y SELL deben ser enteras, aunque la columna permita dos decimales.
- `rejection_reason` debe utilizarse cuando una operación sea rechazada por una regla de negocio.

La columna `size` tendrá un único propósito estructural: representar la cantidad de instrumentos o el importe de una transferencia, dependiendo del tipo de operación.

Para transferencias, `size` representa un importe expresado en ARS.

Para compras y ventas, `size` representa la cantidad de acciones.

### 3.4. Tabla marketdata

Almacena las cotizaciones de los instrumentos.

Los datos serán precargados y su carga o actualización queda fuera del alcance del challenge.

| Campo | Tipo PostgreSQL | Restricciones |
|---|---|---|
| id | BIGINT GENERATED BY DEFAULT AS IDENTITY | PK |
| instrument_id | BIGINT | FK a instruments.id, NOT NULL |
| high | NUMERIC(10,2) | NOT NULL |
| low | NUMERIC(10,2) | NOT NULL |
| open | NUMERIC(10,2) | NOT NULL |
| close | NUMERIC(10,2) | NOT NULL |
| previous_close | NUMERIC(10,2) | NOT NULL |
| datetime | TIMESTAMP WITHOUT TIME ZONE | NOT NULL |

Restricciones:

- Los valores de cotización deben ser positivos.
- `high` debe ser mayor o igual que `low`.
- Debe existir una restricción UNIQUE sobre `(instrument_id, datetime)`.

Para obtener la última cotización se utilizará el registro con mayor `datetime` para cada instrumento.

El campo `close` representa el último precio disponible.

El campo `previous_close` representa el precio de cierre anterior.

### 3.5. Tabla idempotency_keys

Esta tabla permitirá garantizar que una misma operación no sea procesada más de una vez cuando el cliente reintente una solicitud.

| Campo | Tipo PostgreSQL | Restricciones |
|---|---|---|
| id | BIGINT GENERATED BY DEFAULT AS IDENTITY | PK |
| user_id | BIGINT | FK a users.id, NOT NULL |
| idempotency_key | VARCHAR(255) | NOT NULL |
| request_hash | VARCHAR(64) | NOT NULL |
| order_id | BIGINT | FK a orders.id, NOT NULL, UNIQUE |
| created_at | TIMESTAMP WITHOUT TIME ZONE | NOT NULL |

Restricciones:

- La combinación `(user_id, idempotency_key)` debe ser única.
- Cada orden debe estar asociada como máximo a un registro de idempotencia.
- Cada registro de idempotencia debe estar asociado a una orden.
- El hash se calculará utilizando SHA-256 sobre el contenido semántico del request.

La clave de idempotencia se utilizará en todas las operaciones POST de creación de órdenes.

### 3.6. Relaciones entre tablas

- `users` tiene una relación uno a muchos con `orders`.
- `users` tiene una relación uno a muchos con `idempotency_keys`.
- `instruments` tiene una relación uno a muchos con `orders`.
- `instruments` tiene una relación uno a muchos con `marketdata`.
- `orders` tiene una relación uno a uno con `idempotency_keys`.

### 3.7. Tipos de datos en Java

Se utilizarán los siguientes tipos:

| Concepto | Tipo Java |
|---|---|
| Identificadores | Long |
| Importes | BigDecimal |
| Precios | BigDecimal |
| Cantidades | BigDecimal |
| Fechas | LocalDateTime |
| Estados de órdenes | Enum |
| Tipos de órdenes | Enum |
| Lados de operación | Enum |
| Tipos de instrumentos | Enum |

No se utilizarán `double` ni `float` para representar importes o precios.

### 3.8. Índices

Se deberán crear índices para optimizar las consultas principales:

**orders**

- Índice `(user_id, datetime DESC)`.
- Índice `(user_id, status, datetime DESC)`.
- Índice `(instrument_id, status)`.

**marketdata**

- Índice `(instrument_id, datetime DESC)`.

**idempotency_keys**

- Restricción UNIQUE `(user_id, idempotency_key)`.
- Restricción UNIQUE `(order_id)`.

Las restricciones UNIQUE ya proporcionan índices únicos en PostgreSQL, por lo que no será necesario duplicarlos.

## 4. Identificación de cuentas y manejo de errores

Todas las operaciones que dependan de una cuenta deberán recibir el header:

`X-AccountNumber`

El sistema utilizará este valor para buscar al usuario mediante `users.account_number`.

Comportamiento:

- Header ausente: HTTP 400.
- Cuenta inexistente: HTTP 404.
- Cuenta existente: continuar con el procesamiento.

No se implementará autenticación ni autorización.

## 5. Consulta de instrumentos

Endpoint:

`GET /api/v1/instruments`

Permitirá consultar todos los instrumentos disponibles o realizar una búsqueda.

Parámetro opcional:

`query`

Comportamiento:

- Sin parámetro `query`: devolver todos los instrumentos.
- Con `query`: filtrar por coincidencia parcial en `ticker` y/o `name`.
- La búsqueda no distinguirá mayúsculas y minúsculas.
- Si `query` está vacío o contiene únicamente espacios: HTTP 400.
- No se implementará paginación inicialmente.

## 6. Creación de órdenes y transferencias

Endpoint:

`POST /api/v1/orders`

Header obligatorio:

- `X-AccountNumber`
- `Idempotency-Key`

El endpoint permitirá crear cuatro tipos de operaciones:

- BUY.
- SELL.
- CASH_IN.
- CASH_OUT.

### 6.1. Estructura del request

El request deberá contener:

- ticker.
- side.
- type.
- size o amount.
- price, cuando corresponda.

Ejemplo de compra:

```json
{
  "ticker": "YPF",
  "side": "BUY",
  "type": "MARKET",
  "size": 10
}
```

Ejemplo de compra LIMIT:

```json
{
  "ticker": "YPF",
  "side": "BUY",
  "type": "LIMIT",
  "size": 10,
  "price": 25000.00
}
```

Ejemplo de compra utilizando amount:

```json
{
  "ticker": "YPF",
  "side": "BUY",
  "type": "MARKET",
  "amount": 100000.00
}
```

Ejemplo de ingreso de efectivo:

```json
{
  "ticker": "ARS",
  "side": "CASH_IN",
  "type": "MARKET",
  "size": 100000.00
}
```

Ejemplo de retiro de efectivo:

```json
{
  "ticker": "ARS",
  "side": "CASH_OUT",
  "type": "MARKET",
  "size": 25000.00
}
```

### 6.2. Validación de size y amount

El request debe contener exactamente uno de los campos:

- `size`
- `amount`

No se permitirá enviar ambos ni omitir ambos.

Validaciones:

- `size` debe ser un número entero positivo para BUY y SELL.
- `amount` debe ser positivo.
- Las transferencias deben utilizar `size`.
- Las transferencias no permiten `amount`.
- No se permiten cantidades fraccionarias de instrumentos.

Cuando se utilice `amount` para BUY o SELL, el sistema calculará la cantidad máxima de acciones enteras cuyo valor no supere el importe indicado.

El importe sobrante permanecerá disponible en la cuenta.

Ejemplo:

Si una acción cuesta ARS 1.500 y se solicita operar por ARS 10.000:

- Cantidad calculada: 6 acciones.
- Importe utilizado: ARS 9.000.
- Importe sobrante: ARS 1.000.

Si el importe no alcanza para adquirir o vender una acción, la orden deberá persistirse como REJECTED.

### 6.3. Validación del precio

Para órdenes MARKET:

- No se permite enviar `price`.
- El precio se obtiene de la última cotización `marketdata.close`.
- El precio utilizado se registra en `orders.price`.

Para órdenes LIMIT:

- El campo `price` es obligatorio.
- El precio debe ser mayor que cero.
- El precio utilizado será el indicado en el request.

Para transferencias:

- El tipo debe ser MARKET.
- No se permite enviar `price`.
- El precio almacenado será NULL.

Si una operación MARKET no tiene una cotización disponible, deberá persistirse como REJECTED.

Las operaciones LIMIT podrán crearse sin datos de marketdata, porque no necesitan una cotización para validar su precio límite.

### 6.4. Validación de recursos disponibles

Las operaciones deberán validar los recursos disponibles de la cuenta, considerando también los recursos reservados por órdenes NEW.

#### BUY

Para una compra se requiere disponer de efectivo suficiente.

El costo de la operación será:

`size * price`

El efectivo disponible se calculará considerando:

- Ingresos CASH_IN FILLED.
- Retiros CASH_OUT FILLED.
- Compras BUY FILLED.
- Reservas de compras BUY NEW.

Si el efectivo disponible es insuficiente:

- La orden se persiste como REJECTED.
- Se registra el motivo del rechazo.
- No se modifica el saldo efectivo.
- No se modifica la posición.

#### SELL

Para una venta se requiere disponer de suficientes acciones.

Las acciones disponibles se calcularán considerando:

- Compras BUY FILLED.
- Ventas SELL FILLED.
- Reservas de ventas SELL NEW.

Si las acciones disponibles son insuficientes:

- La orden se persiste como REJECTED.
- Se registra el motivo del rechazo.
- No se modifica la posición.
- No se modifica el saldo efectivo.

### 6.5. Comportamiento de órdenes MARKET

Las órdenes MARKET se ejecutan inmediatamente.

Si las validaciones son satisfactorias:

- Se persiste la orden.
- El estado queda en FILLED.
- Se registra el precio utilizado.
- Se actualizan los recursos de la cuenta mediante el movimiento registrado.

Si las validaciones de negocio no se cumplen:

- Se persiste la orden como REJECTED.
- Se informa el motivo del rechazo.
- No se impactan los recursos de la cuenta.

### 6.6. Comportamiento de órdenes LIMIT

Las órdenes LIMIT no se ejecutan automáticamente.

Cuando se recibe una orden LIMIT:

1. Se valida la cuenta.
2. Se valida el instrumento.
3. Se valida el precio límite.
4. Se valida la cantidad o importe solicitado.
5. Se validan los recursos disponibles.
6. Se reservan los recursos necesarios.
7. Se persiste la orden con estado NEW.

Una orden LIMIT permanecerá en NEW hasta que sea cancelada.

No se implementará un motor de matching ni un proceso automático de ejecución de órdenes LIMIT.

#### Reservas de órdenes LIMIT

BUY LIMIT:

- Reserva efectivo equivalente a `size * price`.
- La reserva se calcula utilizando el precio límite.

SELL LIMIT:

- Reserva la cantidad de acciones solicitada.

Las reservas deberán descontarse de los recursos disponibles para nuevas operaciones.

### 6.7. Transferencias de efectivo

Las transferencias se modelarán como órdenes utilizando el instrumento ARS.

#### CASH_IN

Representa un ingreso de efectivo.

Reglas:

- Ticker obligatorio: ARS.
- Tipo: MARKET.
- Se utiliza `size` para representar el importe.
- No se permite `price`.
- Se ejecuta inmediatamente.
- Estado final: FILLED.
- Incrementa el efectivo disponible.

#### CASH_OUT

Representa un retiro de efectivo.

Reglas:

- Ticker obligatorio: ARS.
- Tipo: MARKET.
- Se utiliza `size` para representar el importe.
- No se permite `price`.
- Se ejecuta inmediatamente.
- Estado final: FILLED, si existen recursos suficientes.
- Disminuye el efectivo disponible.

Para validar un CASH_OUT se deberá considerar el efectivo disponible después de descontar las reservas de órdenes BUY NEW.

Si no existen recursos suficientes, se persistirá la operación como REJECTED.

Las transferencias no podrán quedar en NEW ni ser canceladas.

### 6.8. Rechazos de negocio y errores de request

Se deberá diferenciar entre errores de validación del request y rechazos por reglas de negocio.

Errores de request:

- No se persiste ninguna orden.
- Se devuelve el código HTTP correspondiente.

Rechazos de negocio:

- Se persiste la orden.
- El estado será REJECTED.
- Se registra el motivo.
- Se devuelve HTTP 201 Created.

Ejemplos de rechazo de negocio:

- Saldo insuficiente.
- Cantidad de acciones insuficiente.
- Importe insuficiente para operar una acción.
- Ausencia de cotización para una operación MARKET.

## 7. Idempotencia

Todas las solicitudes POST `/api/v1/orders` deberán incluir el header `Idempotency-Key`.

La clave será única por cuenta.

El sistema deberá garantizar que una operación no se ejecute dos veces como consecuencia de reintentos del cliente.

### 7.1. Comportamiento

Al recibir una solicitud:

1. Resolver la cuenta mediante `X-AccountNumber`.
2. Obtener el identificador interno `user_id`.
3. Calcular SHA-256 del contenido semántico del request.
4. Buscar la combinación `user_id + idempotency_key`.
5. Si no existe, procesar la operación.
6. Persistir la orden y su registro de idempotencia dentro de la misma transacción.
7. Si existe y el hash coincide, devolver el resultado original.
8. Si existe y el hash es diferente, devolver HTTP 409 Conflict.

### 7.2. Concurrencia e idempotencia

La restricción UNIQUE `(user_id, idempotency_key)` deberá garantizar que no puedan registrarse dos claves iguales para una misma cuenta.

Las solicitudes concurrentes con la misma clave no deberán generar órdenes duplicadas.

La creación de la orden y el registro de idempotencia deberán ser atómicos.

Si la transacción falla, ambos registros deberán revertirse.

El hash deberá considerar los campos semánticos:

- ticker.
- side.
- type.
- size o amount.
- price.

El cálculo deberá ser independiente del orden de las propiedades JSON.

No se deberán eliminar claves mientras las órdenes asociadas deban seguir siendo idempotentemente consultables.

## 8. Concurrencia y atomicidad

El sistema deberá garantizar consistencia ante operaciones simultáneas sobre una misma cuenta.

Se utilizarán:

- Transacciones de base de datos.
- Bloqueo pesimista mediante `SELECT FOR UPDATE`.
- Restricciones de unicidad.
- Integridad referencial.
- Persistencia atómica de órdenes e idempotencia.

### 8.1. Bloqueo por cuenta

Antes de validar los recursos disponibles, se deberá obtener un bloqueo pesimista sobre el registro correspondiente a la cuenta.

El bloqueo deberá mantenerse durante toda la transacción.

Esto permitirá evitar que dos operaciones concurrentes consuman simultáneamente los mismos recursos.

Todas las operaciones que modifiquen los recursos de una cuenta deberán seguir el mismo criterio de bloqueo.

### 8.2. Atomicidad

La validación de recursos, la creación de la orden, la actualización lógica de los recursos y el registro de idempotencia deberán realizarse dentro de una única transacción.

No se permitirá que una operación quede parcialmente persistida.

## 9. Cancelación de órdenes

Endpoint:

`DELETE /api/v1/orders/{orderId}`

Header obligatorio:

`X-AccountNumber`

Reglas:

- Solo se pueden cancelar órdenes en estado NEW.
- Una orden FILLED no se puede cancelar.
- Una orden REJECTED no se puede cancelar.
- Una orden CANCELLED no se puede cancelar.
- Al cancelar una orden NEW se deben liberar los recursos reservados.

Respuestas:

| Situación | HTTP |
|---|---|
| Orden cancelada correctamente | 200 |
| Orden inexistente | 404 |
| Orden perteneciente a otra cuenta | 404 |
| Orden en estado FILLED | 409 |
| Orden en estado REJECTED | 409 |
| Orden en estado CANCELLED | 409 |

No se deberá revelar la existencia de órdenes pertenecientes a otras cuentas.

La cancelación deberá ejecutarse dentro de una transacción y respetar el bloqueo pesimista por cuenta.

## 10. Respuesta de creación de órdenes

La creación de órdenes devolverá HTTP 201 Created tanto para órdenes FILLED como REJECTED o NEW.

La respuesta deberá contener:

- id.
- ticker.
- side.
- type.
- size.
- price.
- status.
- rejectionReason.
- datetime.

Ejemplo:

```json
{
  "id": 1001,
  "ticker": "YPF",
  "side": "BUY",
  "type": "MARKET",
  "size": 10,
  "price": 25000.00,
  "status": "FILLED",
  "rejectionReason": null,
  "datetime": "2026-11-12T04:30:00"
}
```

Para operaciones rechazadas, `rejectionReason` deberá informar el motivo correspondiente.

## 11. Portfolio

Endpoint:

`GET /api/v1/portfolio`

Header obligatorio:

`X-AccountNumber`

El endpoint deberá devolver el estado patrimonial de la cuenta.

### 11.1. Efectivo

Se deberá informar:

- Efectivo total.
- Efectivo disponible.
- Efectivo reservado.

El efectivo total se calculará a partir de las operaciones CASH_IN y CASH_OUT FILLED.

El efectivo disponible se calculará descontando las reservas de compras BUY NEW.

El efectivo reservado corresponderá al importe comprometido en órdenes BUY NEW.

Las órdenes NEW no modifican el patrimonio total, solamente reducen la disponibilidad.

### 11.2. Posiciones

Se deberá informar para cada instrumento:

- ticker.
- cantidad total.
- cantidad disponible.
- cantidad reservada.
- precio actual.
- valor de mercado.
- costo promedio.
- rendimiento total.
- rendimiento diario.

Las posiciones se calcularán a partir de las órdenes BUY y SELL FILLED.

Las órdenes NEW no modificarán la cantidad total de acciones, pero sí afectarán la cantidad disponible mediante las reservas.

### 11.3. Costo promedio

Se utilizará el método de promedio ponderado.

Las compras FILLED incrementarán la cantidad y el costo acumulado.

Las ventas FILLED reducirán la cantidad utilizando el costo promedio vigente.

Las órdenes NEW, REJECTED y CANCELLED no modificarán el costo promedio.

### 11.4. Rendimiento total

El rendimiento total se calculará mediante:

`((Valor actual - Costo de adquisición) / Costo de adquisición) * 100`

El valor actual será:

`Cantidad total * Último precio close`

El costo de adquisición se determinará mediante el promedio ponderado de las compras FILLED, ajustado por las ventas FILLED.

Si no existe costo de adquisición, el rendimiento deberá manejarse sin producir divisiones por cero.

### 11.5. Rendimiento diario

El rendimiento diario se calculará utilizando la última cotización:

`((close - previousClose) / previousClose) * 100`

Si `previousClose` es cero o no existe información válida, deberá evitarse la división por cero y definirse un valor nulo para el rendimiento.

### 11.6. Patrimonio total

El patrimonio total se calculará como:

`Efectivo total + Valor de mercado de todas las posiciones`

Las órdenes NEW afectan la disponibilidad, pero no el patrimonio total.

El efectivo reservado permanece incluido en el efectivo total.

Las acciones reservadas permanecen incluidas en las posiciones totales.

### 11.7. Cuentas sin operaciones

Una cuenta sin operaciones deberá poder consultar el portfolio sin errores.

Respuesta esperada:

- Efectivo total: 0.
- Efectivo disponible: 0.
- Efectivo reservado: 0.
- Posiciones: lista vacía.
- Valor total del portfolio: 0.

Si la cuenta tiene ingresos CASH_IN FILLED, deberá mostrar el efectivo correspondiente aunque no tenga posiciones.

Si no existen posiciones ni reservas, el valor total del portfolio será igual al efectivo disponible y total.

El endpoint deberá devolver HTTP 200.

## 12. Historial de órdenes

Endpoint:

`GET /api/v1/orders`

Header obligatorio:

`X-AccountNumber`

El endpoint devolverá todas las órdenes pertenecientes a la cuenta.

Se incluirán todos los estados:

- NEW.
- FILLED.
- REJECTED.
- CANCELLED.

El ordenamiento será por `datetime DESC`.

### 12.1. Paginación

Parámetros:

- `page`: página solicitada.
- `size`: cantidad de elementos por página.

Valores por defecto:

- page = 0.
- size = 20.

Validaciones:

- page debe ser mayor o igual a cero.
- size debe estar entre 1 y 100.
- Valores negativos: HTTP 400.
- Valores no numéricos: HTTP 400.
- size mayor a 100: HTTP 400.
- Una página sin resultados deberá devolver HTTP 200 con una lista vacía.

La respuesta deberá incluir:

- content.
- totalElements.
- totalPages.
- page.
- size.

### 12.2. Filtros

Se permitirán los siguientes filtros opcionales:

- status.
- side.
- ticker.

Los filtros podrán combinarse.

`status` permitirá:

- NEW.
- FILLED.
- REJECTED.
- CANCELLED.

`side` permitirá:

- BUY.
- SELL.
- CASH_IN.
- CASH_OUT.

`ticker` realizará una coincidencia exacta.

Los filtros deberán aplicarse siempre dentro del conjunto de órdenes pertenecientes a la cuenta identificada.

Los valores inválidos para status o side deberán devolver HTTP 400.

### 12.3. Detalle individual

El endpoint `GET /api/v1/orders/{orderId}` queda fuera del alcance inicial.

## 13. Fechas y horas

Las fechas se almacenarán utilizando la convención UTC.

Se utilizará:

- PostgreSQL: `TIMESTAMP WITHOUT TIME ZONE`.
- Java: `LocalDateTime`.
- API REST: ISO 8601 sin zona horaria, offset ni sufijo Z.

Ejemplo:

`2026-11-12T04:30:00`

Para obtener la hora actual en UTC desde Java se utilizará:

`LocalDateTime.now(Clock.systemUTC())`

La aplicación deberá mantener la convención UTC en todas las operaciones de persistencia y consulta.

La base de datos no almacenará información de zona horaria.

## 14. Manejo uniforme de errores

Todas las respuestas de error deberán utilizar una estructura uniforme:

```json
{
  "timestamp": "2026-11-12T04:30:00",
  "status": 400,
  "error": "Bad Request",
  "message": "Invalid request",
  "path": "/api/v1/orders"
}
```

Códigos HTTP contemplados:

| Código | Uso |
|---|---|
| 400 | Request inválido o errores de validación |
| 404 | Cuenta, instrumento o recurso inexistente |
| 409 | Conflictos de estado o idempotencia |
| 500 | Errores inesperados |

Los rechazos de negocio de órdenes no se considerarán errores HTTP. Deberán persistirse como REJECTED y responder HTTP 201.

## 15. Endpoints

| Método | Endpoint | Descripción |
|---|---|---|
| GET | /api/v1/instruments | Consultar instrumentos |
| POST | /api/v1/orders | Crear órdenes y transferencias |
| DELETE | /api/v1/orders/{orderId} | Cancelar una orden |
| GET | /api/v1/orders | Consultar historial |
| GET | /api/v1/portfolio | Consultar portfolio |

Todos los endpoints que requieren identificar una cuenta utilizarán el header `X-AccountNumber`.

El endpoint POST `/api/v1/orders` requerirá además `Idempotency-Key`.

## 16. Fuera de alcance

No se implementarán:

- Autenticación.
- Autorización.
- Registro de usuarios.
- Carga de marketdata.
- Actualización automática de cotizaciones.
- Motor de matching.
- Ejecución automática de órdenes LIMIT.
- Integración con mercados reales.
- Integración con brokers.
- Transferencias bancarias reales.
- Tabla de posiciones persistidas.
- Tabla de saldos persistidos.
- Endpoint de detalle individual de órdenes.
- Procesamiento asíncrono mediante SNS/SQS.

## 17. Requisitos no funcionales

### 17.1. Consistencia

Las operaciones deberán ser transaccionales.

No se permitirá modificar parcialmente los recursos de una cuenta.

### 17.2. Concurrencia

Las operaciones que modifiquen recursos deberán utilizar bloqueo pesimista por cuenta.

### 17.3. Idempotencia

Todas las operaciones de creación deberán ser idempotentes mediante el header `Idempotency-Key`.

### 17.4. Precisión monetaria

Todos los cálculos financieros deberán utilizar `BigDecimal`.

En PostgreSQL se utilizará `NUMERIC(10,2)` para importes, precios y cantidades.

No se permitirá utilizar tipos de punto flotante para cálculos monetarios.

### 17.5. Integridad

Las relaciones entre entidades deberán protegerse mediante claves foráneas.

Se utilizarán restricciones UNIQUE y CHECK cuando corresponda.

### 17.6. Mantenibilidad

La solución deberá mantener separación de responsabilidades entre:

- Controllers.
- Services.
- Repositories.
- Entities.
- DTOs.
- Mappers.
- Exception handlers.

Se deberá evitar implementar reglas de negocio directamente en los controllers.
